# ADR-009: Catalog, the use-case layer over the query coordinator

Status: accepted · Date: 2026-10-12 · Amended: 2026-10-16 (plan item P4.9a: the feeds wired; one feed context per nuget.config chain; per-source versions and metadata; readmeImage and prewarm)

## Context

Two surfaces ask the same questions about the same projects, and in 1.x each panel composed the services itself (`NuGetPanel.ts`, `NuGetSidebarPanel.ts`): both computed updates for the same project with their own refresh verbs and caches. ADR-002 gives one computation per resource and generation; ADR-004 and ADR-005 give the project model and its execution context. Missing was the one place where a read request becomes a coordinator query over those modules, so that handlers stay thin and never compose core modules themselves. The quarry's `Catalog.ts` had that role but blocked on the evaluator, fabricated the execution context and took directories from `process.cwd()` (findings C-project-catalog-2, -3 and -6).

## Decision

1. Hosts read through the `Catalog` (`src/core/catalog`) and nowhere else. The Catalog has one method per read request of `RequestMap` (`src/protocol/messages.ts`) plus the two lookups `PackageWorkflows` needs (`packageDependencies`, `projectDependencies`). Every cacheable read is exactly one `QueryCoordinator.query` under the key that `resourceKeys` builds for that request, so both surfaces share one computation per generation. Reads that ADR-002 leaves without a key (`search/query`, `search/autocomplete`, `package/readme`, `transitive/metadata`) run directly. `package/versions` and `package/metadata` are fan-outs over per-source resources: one coordinator query per source the project's policy allows for the id, under `resourceKeys.versions(id, source.url, …)` and `resourceKeys.metadata(id, version, source.url)`, merged in source order; the `'all'` keys of `resourceKeys` stay reserved like the `allProjects:*` keys, and these two responses carry no generation (finding N70). `readme/image` is `readmeImage` and `package/prewarm` is `prewarm`. `transitive/metadata` answers lite metadata for any list of package versions; until P6.2 adds the provisional chunk to `installed/get`, the installed views ask it after `installed/get`, because a chunk precedes the response (ADR-007) and enrichment must not delay the list. The `allProjects/*` methods are fan-outs over the per-project resources and are not coordinator resources themselves: a cache hit delivers the final value and no chunk, and the payload of an all-projects read is its chunks; the `allProjects:*` keys of `resourceKeys` stay reserved.
2. Streams are `emit` callbacks. The chunk types of the all-projects methods are the protocol's `RequestChunk<…>` types (type-only import), so the host forwards them unchanged. The coordinator caches what the compute function returns; a cache hit and a late joiner receive that value and no chunk, so the returned value is complete on its own and chunks only precede it.
3. `installed(projectPath)` resolves as soon as the provisional result exists, with `{ result, upgrade? }`. `upgrade` is present only when an evaluation has started; it resolves with the authoritative result, or with the provisional again when the evaluation fails or the generation is superseded, and it never rejects. The coordinator caches the authoritative result when there is one, so a cache hit and a joiner during the evaluation receive `{ result: authoritative }` without `upgrade`. The host streams the provisional as a chunk and sends the authoritative as the terminal response (ADR-007: chunks precede the response); the chunk kind that carries it is added to `installed/get` by the item that adds the evaluator (P6.2), which also decides when an evaluation is needed. An evaluation never runs for an `unsupported` project.
4. Every project-scoped read builds its `ProjectExecutionContext` through `ProjectContextProvider` (ADR-005), and nothing in `src/core/catalog` reads `process.cwd()`; a read that needs a directory without a project takes it from the caller (`sources(projectDir)`), and the host decides which directory that is. A context whose SDK is below 10 is reported as `InstalledResult.unsupported = { reason: 'sdk-too-old', message: 'requires .NET SDK 10 or newer' }` on the provisional result with its packages kept, because the project stays readable (D13); an `unsupported` set by the inspector is kept as it is. When the context cannot be built, the provisional result stands without evaluation and the failure is logged: a source listing that fails does not hide the package list.
5. Sources, outbound policy and credentials belong to a project context (ADR-005). A Catalog method resolves them from the context of the project the read is for, never from a workspace-wide default; The Catalog keeps one feed context per effective `nuget.config` chain (its sources, package source mapping, outbound policy and the policy-bound feed clients), reached through `ProjectContextProvider.get` for a project-scoped read and through the directory the host names for a read without a project. The service-index client, which owns the source health, and the credential provider are shared; a `nuget.config` credential is looked up across the registered chains, first chain wins, and a source is probed or warmed only after the chain of its directory is registered.
6. `invalidate(scope, reason)` is the single entry for invalidation. It always forwards to `QueryCoordinator.invalidate`; for the scopes `sources` and `workspace` it first clears the per-directory source listings (`SourceProvider.invalidate`), and clears the feed contexts, the service-index caches and health, the icon resolvers, the README-image cache and the credential cache at the same place. A change of health that the monitor finds invalidates nothing; it travels as the `sources/health` event. Caches that check their inputs themselves (the mtime-keyed `AssetsReader`) are not cleared here.
7. A query handle is released when the caller's `AbortSignal` aborts; a call without a signal releases its handle when the value settles. A handle that rejects with `StaleQueryError` is released and the query is asked again, at most three times; the third `StaleQueryError` is thrown.
8. Breadth: no use case is added to the Catalog without amending this record. The feed-dependent reads are `updates`, `allProjectsUpdates`, `transitiveMetadata`, `search`, `quickSearch`, `versions`, `metadata`, `readme`, `readmeImage` and `prewarm`. A feed-dependent answer that is incomplete (`sourcesUnavailable`, `offline` metadata, or no metadata at all) is delivered but never cached: its compute rejects with a carrier of the value and the Catalog unwraps it with the handle's generation, so the coordinator stores nothing (ADR-002 caches successes only).

## Consequences

- Handlers are thin: validate the payload, call one Catalog method, forward chunks, send one terminal response.
- Mutations never go through the Catalog: they are `PackageWorkflows` on the `OperationQueue` (ADR-003). The Catalog learns of them through `invalidate`.
- `search/query` carries `sourcesUnavailable` from the Catalog's `search` result (an unreachable source is not an empty result).
