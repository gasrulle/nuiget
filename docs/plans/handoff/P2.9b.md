> RULING UX-P2.9b (queued operations busy everywhere; the floor proof)

> DECISION: Option B, as a delegated deviation from the plan row's wording, not `OWNER MUST DECIDE`: the e2e test keeps the row's title, `the row menu uninstalls through webview/context`, and runs the command the menu item executes (`vscode.commands.executeCommand('nuiget.row.uninstall', <context object>)`) on `E2E (1.90.0)` and `E2E (stable)`, proving the contributed command, its guard, `settleOperation` and the restore on the floor; right-click and Shift+F10 opening VS Code's menu are proven by a `[menu]` probe in the capture suite, `hard` in the `ui` lane (1.140.0) and the `ui-floor` lane (1.90.0), informational on `ui-macos`. The queued emitter is `HostEvents.operationProgress` (already declared, unused) merged with `queue.onProgress` behind `onOperationProgress`, fired by one host-side helper that every `rowMenu.ts` submission goes through, with `status: 'queued'`, `kind`, `projectPaths` and `packageIds`, only when `ticket.admitted`.

> WHY: An extension-host test cannot reach a webview's DOM (`v2-sidebar.e2e.test.ts:8-14`), so the row's literal e2e is impossible as written; ADR-013's Consequences already assign the menu itself to "ExTester and the E2E job at the floor", so the split keeps the ADR and deviates only from the row's one-sentence output, which is the planning session's call. The 1.90.0 forwarding is now bracketed rather than unverified: VS Code 1.85.0 (`.vscode-test/vscode-darwin-arm64-1.85.0/.../webview/browser/pre/index.html`) and 1.140.0 (`/tmp/nuiget-ui/...`) carry a byte-equivalent `contextmenu` handler (return on `defaultPrevented`, `closest('[data-vscode-context]')` merge, `did-context-menu` with `clientX/Y`), the same `contentWindow.postMessage(message.message, window.origin, message.transfer)` forwarding, the same host dispatch (`createOverlay([...Object.entries(context), ['webviewId', providedViewType]])`, `getActionsContext: () => ({ ...context, webview })`) and both send `set-context-menu-visible` (1.85: one site, with `onDidHideContextMenu` for `visible: false`), which the frame mirrors as `body.vscode-context-menu-visible` in the content document; 1.90 lies between them. The plumbing is in place: `HostEvents.operationProgress` (`src/host/services.ts:171`) is never fired; `onOperationProgress` is `queue.onProgress` alone (`extension.ts:139`), forwarded as `ops/progress` by both hosts (`MainPanelHost.ts:85`, `SidebarHost.ts:38`); `awaitTicket` reports `queued` into the request's stream only (`handlers.ts:187`), which is why a host-submitted operation looks idle (X25). A ticket has `opId` and `admitted` at `submit()` (`contracts.ts:81-88`, `OperationQueue.ts:76-80`), and an idle queue starts the job on a microtask (`OperationQueue.ts:174-176`), so a `queued` event fired right after `submit()` precedes the workflow's first `running` report; the ops slice keeps `queued` in `IN_PROGRESS` (`ops.tsx:32`), merges reports by `opId` keeping the union of paths and ids (`:45-49, :94-96`), drops a report that arrives after the outcome (`ended`, `:88-91`) and answers `isPackageBusy` from the merged entry (`:232`): nothing in the webview changes. The harness runs registered commands through the mock registry (`harness.ts:281-283`, `__mocks__/vscode.ts:258-269`) and reads each surface's events (`fakeWebview.ts:184`), and its scenario at `scenarios.test.ts:160-172` already holds a running operation with others queued, so the named scenario needs no menu.
