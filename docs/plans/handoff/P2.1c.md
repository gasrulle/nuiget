> DECISION: Option 2, in this form: the grouped list is a `role="tree"` whose rows, group rows and package rows alike, are `role="treeitem"` with `aria-level`, group rows carrying `aria-expanded`; a list without groups stays `role="listbox"`/`role="option"`. The role is a property of the consumer (the `groups` prop is given), never of the data. `Listbox` keeps its name and owns the group row's `treeitem`; `groups.render` draws text and decoration inside it. One shared hook, `useBulkSelection`, lands with its test and no consumer. The §8 row triad changes in role name for grouped lists only, and P2.1f carries §8 as the row says; P2.1c does not stop. > WHY: Verified in the tree: `Listbox.tsx:264-275` renders the group wrapper as `role="presentation"` with `tabIndex={-1}` and focuses the first `FOCUSABLE` control of `renderGroup`'s output (:25-26, :129-135); `Row.tsx:121-135` renders `role="option"` with `aria-posinset={index + 1}` and `aria-setsize`; `primitives.css:80-87` positions every row absolutely in `.nuiget-listbox-sizer`, so the virtualization is flat. axe-core 4.12.1's role table (`node_modules/axe-core/axe.js:14671-14678`) gives `option` `allowedAttrs` of `aria-selected`, `aria-checked`, `aria-posinset`, `aria-setsize` only, so the brief's probe A (`aria-expanded` on an option fails `aria-allowed-attr`) is the table, not an accident; `treeitem` (:14921-14927) allows `aria-expanded`, `aria-level`, `aria-posinset`, `aria-selected`, `aria-setsize`, requires a `group` or `tree` context and has no `childrenPresentational`, and `tree` (:14908-14913) owns `group` and `treeitem` and allows `aria-multiselectable`. Two mechanisms close the listbox shapes: `getOwnedRoles`, the evaluator of `aria-required-children`, descends into a `group` whenever `group` is a required child of the parent (it is for `listbox`) and files any descendant with a role, a global ARIA attribute or focus as an owned role, so a button or a focusable wrapper as the group header inside `listbox > group` is `unallowed` exactly like probe D, and the only header a listbox admits is an `option`, which cannot say it is expanded (probe A); and a zero-box `role="group"` wrapper under the clipping `.nuiget-listbox` is the condition under which axe hides descendants (gotcha "`display: contents` and axe", P9.2), so the brief's "a flat virtualized list cannot nest options inside group elements" stands. That leaves the tree against an option that hides "expanded" in a word (the brief's option 3). ADR-013 Decision 8's key table (Right expands or moves to the first child, Left collapses or moves to the parent, Up/Down cross groups, Home/End, Enter toggles) is the APG tree-view pattern verbatim, and the workbench's own collapsible single-scroller lists (Explorer, Source Control, Search) are its tree widget with `treeitem`, `aria-level` and `aria-expanded`, cited from VS Code's list widget source, not from `docs/design/workbench/*.json`, which carry no roles (checked: no `"role"` key in `modern.json`); the plan row names that widget as the alternative.
