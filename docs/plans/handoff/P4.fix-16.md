### 2026-11-19, UX-P4.fix-16, design-advisor opening ruling

Question: the focus mechanism and target, the toast form, the tests, the captures, the files.

> DECISION: Focus: option 1 with a preliminary fix. A feature hook in the Installed tab, modelled on `useHiddenDetailsFocus`, moves the focus when the restore banner leaves with the focus in it. The target is the Transitive group row when it is in the document, else the tree's active row, else `restoreFocus`'s order. Before that, the single-project banner must stop being remounted when the restore starts. Toast: option (a), scoped to kind `restore`. One of two projects restored reads `nUIget: Restored 1 of 2 projects; 1 failed.`
>
> WHY:
> - **The brief's premise is probably wrong on the single-project path.** `transitiveTree` returns a bare `<Banner>` when not loading and `<><ProgressBar/>{message}</>` when `restoring` (`TransitiveSection.tsx`, last line of `transitiveTree`). The slot `{transitivePart.message}` in `InstalledTab.tsx` therefore flips from Banner to Fragment at the press, and React recreates the banner. The focus would fall to `<body>` when the restore starts, not when the banner leaves. This is read from the code, not run. The existing case at `InstalledTab.test.tsx:331` cannot see it, because every press is a `user.click`, which focuses the button again.
> - **All Projects has the stable shape already** (`{restoring ? <ProgressBar/> : null}` first, then the banner), so its button survives until the last project is restored.
> - **Target.** The tracker row and DO 14 of UX-P4.fix-10 fix it as the Transitive group row; the banner speaks for that group. `Listbox`'s `onFocus` makes any focused row the active row and tab stop (`Listbox.tsx:436-441`), so no `ListboxProps` diff is needed. The tree is virtualized and only the active row is guaranteed rendered, so the fallback is A6's own order (DECISIONS 2026-11-17, UX-P4.4).
> - **Mechanism.** It follows the UX-P4.fix-6 ruling (DECISIONS 2026-11-18): only for focus that was in the element that left, only while `document.hasFocus()`, else on the window's next `focus`; no timer, retry or `MutationObserver`. A restore takes seconds and the user may be in an editor when it ends. Option 2 changes `BannerProps` (trigger 5; DO NOT of the UX-P4.fix-10 ruling) and lands on the wrong row. Option 3 reads `document.activeElement` after React has already removed the button.
> - **Toast.** For a restore, `results` and `restores` hold the same projects (`PackageWorkflows.ts:103-119`), so the second clause repeats the first. For install, update and remove the two clauses count different things (packages against projects), so `feedback.test.ts:98-99` are correct and option (c) is wrong. The form matches the webview's "Restored 1 of 2 projects" (DECISIONS 2026-11-18, UX-P4.fix-10).
